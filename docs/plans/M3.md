## Goal

Core follows the accepted links through the events. Every event that carries an accepted key
lands in exactly one transaction, a nightly file with thousands of records becomes one batch
linked to its transactions instead of one giant transaction, and the transactions feed a flow
graph with hop statistics and clock skew estimates. A person types any system's identifier into
search, core asks the edge for its tokens, and the trace view shows the whole path as a
timeline. A person with the reveal grant and a fresh login sees the values behind the tokens,
fetched from the edge and never stored in core. The map screen shows the systems and hops with
volume and latency, and the eval harness scores assembly and batch detection against simulator
truth.

## How the engine runs

1. `ingest-api` and `load-bundle` keep writing `events` and `event_identifiers` (M1), the
   profiler and linker keep the map (M2).
2. The worker gains two job kinds. `assemble` runs every 30 s by the `stored_at` watermark of
   `event_identifiers` (ADR 0046); `graph` runs after every assemble pass for the hop rollup
   and nightly for the previous day's hourly rebuild, terminal nodes, flow variants and clock
   skew. `payload['full']` on `assemble` reassembles the window from scratch into new
   `txn_events` versions (after a link rejection, a new batch key, nightly when
   `assembler.nightly_rebuild` is on, or by hand with `carto-core reassemble`).
3. The assembler asks the store for the events stored since the watermark, within a window of
   the entity's max span plus a day, together with their identifier tokens restricted to the
   **key ends**: the `(field_ref, form)` ends of accepted or auto-accepted exact and bridge
   links with the transaction role, plus (question 1) the explicit event pairs of accepted
   composite links (`composite_matches`, persisted by the link pass from M3 on; M2 computes
   them per pass in memory and keeps none). Batch keys are excluded from the merge keys.
4. For each micro-batch it resolves the keys against `txn_token_index` in one PostgreSQL round
   trip (`token = ANY($1)`), runs union-find in memory over the batch, applies the hub rule
   and the guardrails, then writes in one PostgreSQL transaction under a per-tenant advisory
   lock: new and updated `transactions`, index upserts, `txn_merges`, `batch_keys`, `batches`,
   `batch_txns` and the `ambiguous_merges` counter on the responsible link. `txn_events` rows
   (new versions for moved events) and `hop_transitions` rows go to ClickHouse next, and the
   watermark moves last, in a second short PostgreSQL transaction, once the ClickHouse insert
   has returned. A crash anywhere repeats the micro-batch from the old watermark: the index
   upserts and the ClickHouse rows are idempotent (same `(txn_id, event_id)` key, higher
   version), so the repeat changes nothing.
5. The graph pass reads the hourly rows and the surviving transactions of one 14-day window
   into the `hops` rollup (support, `p_next`, p50/p95/p99 from one population), computes
   terminal nodes per entity from settled transactions, the top 10 flow variants per entity,
   and the per-system clock offsets from the accepted links whose direction is known.
6. The API serves traces, batches and the graph from PostgreSQL and ClickHouse; search and
   reveal go to the edge over mutual TLS with core's `api` role certificate (ADR 0031) and an
   Ed25519-signed assertion (M1 plan decision 13, `carto_common.crypto`), through an
   `EdgeTransport` Protocol so the hosted model of Section 22.4 replaces the transport and not
   the routes.
7. `carto-core discover` runs profile, link, assemble and graph once over a loaded bundle and
   writes the prediction files; search is not available over a bundle (no edge to tokenize),
   traces are reached from the map, the review items and the batch list.

The store Protocol (`carto_core.store.EventStore`) gains the queries the assembler and the
graph need, each implemented in ClickHouse and in the in-memory fake and covered by the
contract suite: events since a watermark within a window with their key tokens, severity and
`ingested_at`, the events of a transaction, the events that carry a token, hop transition
inserts, hourly hop stats over a window, and the terminal-node counts. The index, the
transactions and the batches live in PostgreSQL behind an `AssemblyIndex` Protocol with a
PostgreSQL implementation and an in-memory one, so the pure logic (union-find, hub rule,
guardrails, status, ordering) is unit-tested without a database and the eval runs in memory as
in M2.

## Decisions proposed with this plan

Each becomes an ADR (0060 onward) when code starts. Decisions marked "spec change" edit the
spec and wait on the founder question named; the rest refine it.

1. **Merge keys are the ends of accepted transaction links plus composite event pairs.**
   *Spec change, question 1.* An event's keys are its tokens in the `(field_ref, form)` ends of
   key links whose status is `accepted` or `auto_accepted`, whose type is `exact` or `bridge`
   and whose role is `transaction`. Association links never merge (spec 9.3). A composite link
   has no shared token, so the link pass persists the matched event pairs it already computes
   (`composite_matches`: tenant, link id, the two event ids, the posterior, matched at; upserted
   per pass on `(tenant_id, link_id, event_id_a, event_id_b)` because the matcher runs over the
   whole linker window each pass; pruned with the events' retention) and the assembler treats
   each pair as a union of the two events' transactions. Spec 9.7 item 1 names only transaction
   links and bridges; without the pairs no composite hop exists (spec 11.1) and scenario C
   cannot reach the F1 target. Tokens of different key versions never compare equal, which is
   how "links per key version" (spec 8.4) holds without code.
2. **The index is PostgreSQL, the micro-batch is resolved in memory.** `txn_token_index` is
   keyed `(tenant_id, token)`; one `SELECT ... WHERE token = ANY($1)` per micro-batch, union-find
   over the batch, one write transaction with batched upserts. The pass takes
   `pg_try_advisory_xact_lock` on a key of its own (`tenant_id`, `'assemble-pass'`, distinct
   from the enqueue dedupe lock on `hashtext('tenant/assemble')`, which would otherwise block
   every `ensure_recurring` behind a running pass) for its write transaction and skips the
   round when the lock is not granted: the queue's dedupe matches only unleased rows,
   `ensure_recurring` enqueues every loop and an expired lease is retaken, so the lease alone
   lets a second worker run a second pass (`core/carto_core/jobs.py`, `jobs_postgres.py`,
   `worker.py`). The worker's docstring claims the opposite ("two workers never pile them up")
   and is corrected in wave 0; the same try-lock wraps the M2 profile and link passes, whose
   concurrent `replace_all` calls can delete each other's entities (latent: Compose runs one
   worker). Merges go into the oldest transaction (smallest ULID,
   `carto_common.ids`: millisecond-ordered, random low bits, deterministic for a given pair of
   ids, which is all the rule needs), so `txn_events` rows are only ever moved from a
   merged-away transaction into a survivor; a trace read is `txn_id = ?` on a surviving id, and
   every reader that starts from an event (search, `LinkView.examples`, the membership export)
   takes `argMax(txn_id, version)` per event, because the table's sort key includes `txn_id`
   and a moved event keeps its old row under the merged-away id. A merged-away id stays in
   `transactions` with `merged_into` set and answers 303. The read window is bounded by the
   entity's max span plus a day (question 13); an event older than that waits for the nightly
   `full` pass.
3. **Hubs are bounded, not undone.** Spec 9.7 counts distinct transactions per token per day.
   The index keeps that count per token and day (`txn_token_fanout`): the number of distinct
   transactions the token has been seen with before merging through it. Ends of batch-role
   links (spec 9.3) start as batch keys and never merge. A transaction-role token whose daily
   count passes `fanout_threshold` (50) becomes a batch key: it leaves the merge index, a
   `batches` row is created, and the transactions that carried it are linked through
   `batch_txns`. Merges the token caused before the threshold stay (at most 50 transactions,
   far under the 10,000 guardrail); the nightly full reassembly (`assembler.nightly_rebuild`,
   on by default, question 2) repairs them. Union-find has no split, and deferring every merge
   until a token's day is complete would cost the 30 s latency the spec wants for traces.
4. **Hop statistics are kept by the store, corrected nightly.** ClickHouse holds
   `hop_transitions` (one row per consecutive node pair: hop, the two event ids, `observed_at`
   of the sending event, latency, error flag, and the sending event's low-cardinality
   attributes so M4 can baseline partial failures by slice (spec 10.2) over a table that cannot
   be backfilled; TTL as events). A materialized view feeds the current day's rows of
   `hop_stats_hourly`, an `AggregatingMergeTree` (count, `countIf` error, a `quantilesDD`
   DDSketch state), whose parts merge the states of the many insert blocks an hour receives at
   2,000 events/s. The nightly `graph` pass recomputes the previous day's hourly rows from the
   ordered surviving transactions (`merged_into IS NULL`, one row per event by
   `argMax(txn_id, version)`) and writes them with a higher `version` into a second table,
   `hop_stats_hourly_rebuilt`, a `ReplacingMergeTree(version)` keyed `(tenant_id, hop, hour)`
   holding finished sketches; the rollup reads the rebuilt table for closed days and the
   streamed table for the current day, so merges that interleave events and moved events are
   corrected within a day. The two engines stay separate because a replacing table would keep
   one insert block per hour and an aggregating table cannot retract states. The PostgreSQL
   `hops` row is the rollup over the 14-day window (support, `p_next`, p50, p95, p99) read
   from the hourly rows and the surviving transactions of that window, one population, which
   the API and the detector (M4) read. `quantileDD` ships in ClickHouse 24.1
   and later; Compose and CI run `clickhouse/clickhouse-server:24.8`, which becomes the floor
   recorded in the ADR. The in-memory store computes exact quantiles; the contract suite
   compares the sketch to them within its relative accuracy (0.01), not bit for bit. Every
   ClickHouse table with a TTL carries `observed_at`, because `apply_retention` reads TTLs of
   that shape only.
5. **Grouping templates into an event type is a view-time mapping.** A `nodes` row exists per
   `(system_id, template_id)` (`id = system_id/template_id`) and per event type group
   (`id = system_id/~label`); `templates.event_type_label` (already a column) is the grouping
   key; `nodes.display_name` is the only display name (`templates.display_name` stays unused)
   and defaults to the template id and kind, never `template_text`, which is customer
   influenced (ADR 0056). `PATCH /nodes/{node_id:path}` sets `display_name` and
   `event_type_label`, is audited (invariant 6) with names and version only, and carries a
   real `version` column for the `ETag` (ADR 0058 item 2). The map, the traces and the `hops`
   rollup aggregate template-level hops by event type when one is set. No `txn_events` or
   `hop_stats_hourly` row is rewritten by a naming decision. Terminal status is computed per
   entity, never patched, in `terminal_nodes(entity_id, node_id, share, computed_at)` (spec
   7.3 had it per node). An LLM name suggestion stays in `suggested_name` and reaches
   `display_name` only through a patch (invariant 5).
6. **Clock offsets need a direction the lag sign cannot give.** *Spec change, question 4.*
   The linker directs a link `a_to_b` only when `lag_positive_share` is at least 0.8
   (`linker/score.py`), so a stored directed link never carries a negative `lag_median`: a
   consistently negative lag is stored as `b_to_a`, and spec 9.8's rule as written selects
   nothing. Skew evidence is an accepted exact link whose recorded direction disagrees with
   the sign of its lag, which needs a direction known independently: `POST /links/{id}/accept`
   gains an optional `direction`, audited as a decision, and links inside one system anchor
   the walk. Such a link with `evidence_json.lag_iqr_seconds` under `tight_lag_iqr_seconds`
   (10) contributes `|lag_median_seconds|` as a lower bound on the offset between its systems.
   Offsets are solved per system relative to the system with the most such links (offset
   zero) and live in `system_clock_offsets(system_id, offset_ms, estimated_at, link_count)`,
   not on `systems`, whose `ETag` is `updated_at` and would turn every graph pass into a
   reviewer's 412. Used in the assembler's ordering key (`observed_at + offset`) and nowhere
   else; the map and the timeline warn when an offset exceeds 30 s. Scenario A's Warehouse is
   +90 s in truth (`ground_truth/sources.json`, fault f6) but every hop into it lags 60 to
   300 s automated or clerk hours and the hop out of it lags hours, so no lag turns negative
   and the estimator yields no evidence on A; the eval prints planted and estimated offsets or
   "no evidence" per system, and the within-5 s property runs on a synthetic scenario with a
   tight reverse hop (question 4 asks whether scenario A should plant one).
7. **Core reaches one edge, through a replaceable transport.** `ApiSettings.edge` holds the
   edge-gateway base URL, the CA file and core's client certificate and key (role `api`, from
   `carto-ctl pki init`, already issued and mounted in Compose). `EdgeClient` implements an
   `EdgeTransport` Protocol and every call names an `edge_id` (ADR 0050), because a hosted
   core (spec 22.4) cannot dial a customer-side edge under spec 5.5 and 14.5 and will replace
   the transport, not the routes. Absent, search and reveal answer 503 `search_unavailable` /
   `reveal_unavailable` and the console says the install has no edge. Several edges per core
   are an M6 question with the control plane.
8. **Search is audited at the edge, counted in core, and the edge's quota is the ceiling.**
   *Spec change, question 3.* The edge already writes one audit row per tokenize call with the
   subject, purpose and core's request id (M1; no IP or user agent, and `purpose` is shape
   masked). Core does not write an audit row per search; its audit log is for actions that
   change something or reveal something (spec 12, 14.9, invariant 6), while spec 8.4 and threat
   3 rest on the edge row. The edge's tokenize quota today is the reveal setting
   `values_per_user_per_hour` (100) applied to queries, so the plan's 60 searches per minute
   would be refused after 100 and package D mapped the 429 to 502. M3 adds
   `reveal.queries_per_user_per_hour` (600) at the edge as the ceiling, sets core's
   `search_per_user` to 10 per minute as a burst cap (600 per hour, so a user at the core rate
   never meets the edge's limit), and passes an edge 429 through with its `Retry-After`; the
   console's 429 message names the hourly ceiling. Core's per-address limit waits for the
   proxy allowlist (M6): `client_ip` ignores `X-Forwarded-For`, which the web proxy sets, so
   one bucket would serve every user behind it. Core keeps
   `search_counters(tenant_id, subject, hour, count)` in PostgreSQL for the M4 self-alert
   (threat 3), written by the API process, so `carto_app` holds INSERT and UPDATE on that one
   table and nothing else of migration 0005; the in-process token buckets are per replica and
   pruned. `search` is named as the assertion's permission (the edge expects one;
   `Permission` has none today).
9. **Step-up is the session's own authentication time.** `Principal.authenticated_at` (M2)
   holds the identity provider's `auth_time` or, when the provider sends none, the callback
   time. `POST /reveal` requires it within `api.oidc.step_up_max_age_seconds` (15 minutes,
   exists) or answers 403 `step_up_required` with `GET /auth/login?max_age=0&return_to=`.
   The login route gains `max_age` and `return_to` (a path under the console origin only,
   stored with the login attempt), the code flow sends `max_age=0` and `prompt=login`, and the
   callback replaces the current session's authentication time and redirects to `return_to`,
   keeping the session id and CSRF token. None of this is wired today: `OidcClient.begin`
   sends neither parameter, `GET /auth/login` takes none and the callback issues a new session
   and redirects to `/`; ADR 0052's "step-up (`max_age`) is wired" is corrected by an amendment
   of 2026-10-28. Dex does not honor `max_age` but has no persistent login for its password
   connector, so the Compose test still re-enters the password; the unit tests use the fake
   provider.
10. **The reveal grant is per user, as M2 built it.** *Question 10.* `users.reveal_granted`
    (migration 0004) is read at login into the session and `Principal.reveal_granted`; the
    plan's `role_bindings.reveal_granted` would duplicate it with group semantics, and
    `bootstrap_group_roles` is a map of group to role with no room for a flag. M3 adds the
    setters only: `carto-core grant-reveal <subject> [--revoke]` (audited, admin only; a role
    change without step-up until the Admin screen exists, recorded as such) and
    `api.bootstrap_reveal_subjects` for the dev profile. `permissions_of` never adds `reveal`
    to a principal holding `auditor` (today it adds it for any role), and the matrix test runs
    every operation a second time as each role with the grant set.
11. **Reveal is one audit row, values pass through once.** Core forwards the edge's values to
    the client in the response body with `Cache-Control: no-store` and holds them in no log,
    cache, session or database. The audit row is `action=reveal`, `target=<transaction or link
    id>`, `reason=<purpose>`, `after={"value_count": n, "missing_count": m}` with the request
    id; no key may contain `token` or `key`, because `audit.scrub` drops those on write. The
    API's logging test posts a planted marker through the reveal path and scans the log
    stream. The console calls reveal as a mutation whose result lives in component state only
    (never a TanStack query, whose cache keeps data for five minutes), shows the values in the
    distinct style for 60 s and clears them on unmount.
12. **Transaction status in M3 is `in_progress`, `completed` or `errored`.** `completed` when
    the current node is terminal for the entity or the transaction is settled (no event for the
    entity's quiet span, spec 9.8); `errored` when the last event's severity is `error` or
    `fatal` (`carto_schema.event.Severity`; `events.severity` is nullable); `stalled` is set by
    the detector in M4. Precedence: `stalled`, `errored`, `completed`, `in_progress`. Ordering
    ties break by `ingested_at` then `event_id` (the canonical event has no source sequence; the
    edge's record sequence is dropped before core). A transaction's entity is the family of its
    first key; `entities.max_span_days` (default 14) is editable through `PATCH /entities/{id}`.
    Family ids are content hashes of the member set rebuilt by every link pass
    (`linker/families.py`, `repository.replace_all`), so a `transactions.entity_id` would
    dangle when a family grows; question 9 decides between stable entity ids and span
    inheritance. Two hazards on `entities` exist today and wave 0 fixes them before the
    assembler reads the table: `replace_all` stamps `updated_at = now` on every entity on every
    link pass whether or not it changed (`repository.py`, the `ON CONFLICT` set list), and the
    entity `ETag` is `updated_at` in milliseconds (`api/data_ports.py`), so a reviewer's
    `PATCH /entities/{id}` answers 412 whenever a pass ran between the GET and the PATCH
    (about every five minutes with `link_after_profile`); and because `replace_all` upserts
    an explicit column list, `max_span_days` would reset to the default when a family grows.
    `entities` gains a real `version` column bumped by reviewer patches only (ADR 0058 item 2,
    as `key_links` has), `replace_all` leaves `version`, `updated_at` and `max_span_days`
    alone on rows it did not rename or re-member, and `FamilyBuilder.rebuild` re-reads the name
    it is about to upsert after the LLM namer returns, so a `set_name` that landed meanwhile
    is not reverted.
13. **Every 9.7 and 9.8 number is a setting** (`AssemblerSettings`, `GraphSettings`), as M2
    did for 9.1 to 9.6 (ADR 0055): micro-batch interval, read window margin, read row cap,
    fanout threshold, max events, default max span, expiry, nightly rebuild, terminal share,
    quiet-span multiplier, variants count and minimum support, tight-lag IQR, skew warning.
14. **Eval policy carries over, with two additions.** Links the M2 policy counts as accepted
    (ADR 0049 decision 5) plus composite links at their stored threshold (if question 1 is yes)
    are the key ends of an eval run, and batch-role links at the proposal threshold count as
    accepted too, because ADR 0049 item 2 counts transaction-role links and bridges only and
    scenario A's batch keys are all batch-role ends (L09, L10, L14, L15). The membership file is
    keyed by engine `event_id`; the driver inverts the locator map (ADR 0024; today it keeps
    only the source prefix) to locator keys for `transaction_pairwise_f1`, which exists.
    Predicted batches carry tokens while `batch_key_precision_recall` compares clear key
    values, so the driver resolves each predicted batch to the truth `key_value` by the majority
    `batch_id` of the events of its linked transactions (`TruthEvents` keeps `batch_id` per
    key), and only when at least 0.8 of those events agree; a predicted batch below that share
    resolves to nothing and counts as a false positive, otherwise any wrong batch would map to
    some truth value and precision could never fall. The analyzer's reveal vault is not used,
    so no value enters the eval process. Extra
    measurements (merge refusals, hub detections, offsets, hop latency, terminals) go to the
    Markdown appendix and `<scenario>.mapping.json`, since `build_report` admits only the spec
    18.4 metric ids. CI restores `history.ndjson` from the previous run of the same branch
    (actions/cache keyed by scenario), passes `--enforce-regressions`, and posts the deltas as
    a PR comment; `--enforce-targets` stays off until the founder accepts scenario C. Today CI
    uploads the report and restores nothing, and neither enforce flag is passed.
15. **Load tests live in the eval package and run on the reference node.** `make load` (new;
    `bench`, `bench-gateway` and `bench-linker` exist) drives the existing gateway benchmark
    (ADR 0028) at 2,000 events/s with the assembler running, a search load and the list
    endpoints against the API; the spec names k6 for the API load. k6 is AGPL-3.0, so it runs
    as a container in CI and on the reference node and is never shipped or imported
    (question 12).
16. **Trace responses carry identifiers; search responses never carry tokens.** The Reveal
    button needs tokens to send (`POST /reveal` takes tokens; spec 13 keeps them behind
    "Details"), so `TraceEventView.identifiers` lists field, form, shape and token per event.
    `SearchResponse` returns transaction and batch summaries and the forms that matched (which
    needs the edge to label tokens by form; the flat list it returns today cannot say).
    `BatchView` never echoes `batches.token`. Core's reveal models are `RevealCall` and
    `RevealResult`, because `carto_edge.reveal` already owns `RevealRequest` and
    `RevealResponse`.
17. **Search is tokenize, then find.** `tokenize(query)` goes to the edge; `find(tokens)`
    answers from `txn_events` and `batch_keys` and is the function the v2 case search of
    spec 22.2 reuses, since the data plane will compute tokens itself and core must answer
    from tokens alone.
18. **The assertion names its key and its request.** `InternalAssertion` gains `key_id` (the
    signer's public key fingerprint) and `request_hash` (SHA-256 of the sorted token list, or
    of the NFKC query); the edge verifies both, accepts `assertion_previous_public_key_file`
    beside the current key so a signer rotation is not an outage, and rebuilds used nonces and
    quotas from its audit file at start (`docs/plans/M1-review-fixes.md` item D, unbuilt: today
    a restart inside the 60 s lifetime accepts a replay). Whether the edge should also receive
    `authenticated_at` and check step-up itself is question 11.
19. **Problem details carry a type.** `Problem` gains `type` (`urn:carto:problem:<name>`) so
    `step_up_required`, `search_unavailable` and `reveal_unavailable` are machine-readable;
    today `about:blank` is hard-coded.
20. **Journey 4.4 runs against the Compose stack.** Spec 18.5 names the stack; today Playwright
    drives `vite preview` with the mocked API and the compose job has no browser step. The
    compose job installs Playwright, signs in through Dex's password connector, and runs the
    search, timeline, step-up and reveal journey; the mocked runs stay for the XSS corpus, axe
    and the review journey. A 390 x 844 project covers the phone-width search and timeline.
